# Soul of Waifu server API (client/server split)

Status: draft for review, API version 1.

The app is split into a light UI client and a server stack run with docker compose. The
server can run on the same PC or on another machine; the client reaches it by URL + token.

## Components

| Where | What | Notes |
|---|---|---|
| Client | Qt UI, Live2D, VRM (WebEngine), characters, chats, Soul memory storage | No torch, no CUDA |
| Client | Microphone capture, Silero VAD (ONNX, `onnxruntime`), audio playback | Devices are on the user's machine; only speech segments leave it |
| Client | ElevenLabs, other cloud LLM/TTS providers | API keys stay on the client |
| Server `llama` | Official `ghcr.io/ggml-org/llama.cpp:server[-cuda\|-vulkan]` in router mode (`--models-dir`) | Models load/unload through its API, no container restarts |
| Server `speech` | XTTSv2, Kokoro, Silero TTS, Qwen3-TTS, Edge TTS, RVC, faster-whisper, e5 embeddings, go-emotions | One process: one torch install, one CUDA context, one VRAM manager |
| Server `gateway` | Token auth, TLS, routing, capabilities, model and voice management | The only published port |

`llama` and `speech` are reachable only on the compose network; everything goes through
the gateway.

## Transport and auth

- Base URL: `http://127.0.0.1:8765` in local mode (bound to loopback only);
  `https://<host>:8765` in server mode.
- Every request carries `Authorization: Bearer <token>`. The token is generated by the
  installer (32 random bytes, urlsafe base64) and kept in the server's `.env`.
- TLS in server mode: the installer generates a self-signed certificate. The client pins
  its SHA-256 fingerprint (trust on first use, like SSH), so no CA or domain is needed.
- Pairing string printed by the installer (also as a QR code):
  `sow://<host>:<port>#token=<token>&fp=<sha256 hex>`; `fp` is absent for plain-HTTP
  local mode. The client accepts it in one field.
- Errors: JSON `{"error": {"code": "...", "message": "..."}}` with a matching HTTP status.
  Codes used by the client: `unauthorized`, `engine_unavailable`, `model_missing`,
  `out_of_vram`, `busy`, `bad_request`, `internal`.

## Endpoints

OpenAI-compatible endpoints are used wherever one exists, so the client also works with
other servers for those features, and the server can be tested with standard tools.

### Service

`GET /sow/health` - no auth; `{"status": "ok", "api_version": 1}`. Used by the installer
and compose healthchecks.

`GET /sow/capabilities`

```json
{
  "api_version": 1,
  "server_version": "2.5.1-linux.1",
  "gpu": {"backend": "cuda", "name": "NVIDIA GeForce RTX 5060 Ti", "vram_total_mb": 16311},
  "llm": {"available": true, "models": ["Qwen3-4B-Instruct-2507-Q4_K_M"], "loaded": "Qwen3-4B-Instruct-2507-Q4_K_M"},
  "tts": [
    {"engine": "kokoro", "available": true, "device": "cuda", "voices": ["af_heart", "..."]},
    {"engine": "xtts", "available": true, "device": "cuda", "voices": ["Female Calm", "Female", "Male"]},
    {"engine": "qwen3", "available": false, "reason": "does not fit into the VRAM budget"},
    {"engine": "silero", "available": true, "device": "cpu", "voices": ["xenia", "..."]},
    {"engine": "edge", "available": true, "device": "cloud"}
  ],
  "rvc": {"available": true, "models": ["Holo"]},
  "stt": {"available": true, "models": ["small"], "device": "cuda"},
  "embeddings": {"available": true, "model": "e5-small-en-ru"},
  "emotions": {"available": true, "labels": ["admiration", "...", "sadness"]}
}
```

The client builds its engine/voice lists from this and hides what is unavailable, with the
`reason` as a tooltip.

`GET /sow/status` - live state for the UI's hardware panel:
`{"gpu": {..., "vram_used_mb": 9120}, "loaded": [{"component": "tts:kokoro", "vram_mb": 420}, ...], "queue": 0}`.
Replaces the client's `torch.cuda` checks (main.py, interface_signals.py).

### LLM - proxied to `llama`

`/v1/chat/completions`, `/v1/completions`, `/v1/models`, streaming included, passed through
unchanged. The client's existing external-server mode (`local_endpoint.py`, Bearer token
from `LOCAL_LLM_API_TOKEN`) works as is.

`GET /sow/llm/models` - GGUF files on the server with size and `loaded` flag.
`POST /sow/llm/load {"model": "<name>", "ctx": 16384}` - load through llama router mode.
`GET /sow/llm/catalog` - curated model list with the VRAM each needs at a given context
(the same catalog the installer uses).
`POST /sow/llm/download {"catalog_id": "..."} | {"url": "https://huggingface.co/..."}` -
starts a download job, returns `{"job": "<id>"}`. `GET /sow/jobs/<id>` - progress.
Downloads are restricted to huggingface.co URLs.

### TTS

`POST /v1/audio/speech` - OpenAI shape plus a `sow` object for engine-specific options.
The client sends what it now reads from the character config; the server is stateless
about characters.

```json
{
  "model": "kokoro",
  "input": "Hello there.",
  "voice": "af_heart",
  "response_format": "wav",
  "sow": {
    "language": "en",
    "rvc": {"model": "Holo", "f0up_key": 0, "index_rate": 0.75, "protect": 0.5},
    "qwen": {"mode": "cloning", "model_size": "1.7B", "device": "cuda",
             "prompt": "", "style_instruct": "", "ref": "<sha256>", "ref_text": "...",
             "language": "English"}
  }
}
```

- `model`: `xtts`, `kokoro`, `silero`, `qwen3`, `edge`. ElevenLabs stays on the client.
- `rvc` is optional; when present the result goes through RVC with that model.
- Response: `audio/wav` body (`response_format: "opus"` later, for remote links).
- Headers: `X-Sow-Sample-Rate`, `X-Sow-Duration`.

`PUT /sow/voices/refs/<sha256>` - upload a reference clip (Qwen3 cloning, XTTS custom
speaker). Content-addressed: the client hashes the local file, `HEAD` tells whether the
server already has it, so there is no sync state. Max 20 MB, wav/mp3/flac/ogg.

`GET /sow/rvc/models`, `PUT /sow/rvc/models/<name>` (multipart: `pth`, optional `index`),
`DELETE /sow/rvc/models/<name>`.

`POST /sow/tts/preload {"model": "qwen3", "sow": {...}}` - load the engine ahead of the
first sentence (the client already does this outside the per-sentence timeout).

### STT

`POST /v1/audio/transcriptions` - multipart: `file` (wav, 16 kHz mono from the client's
VAD segment), `model` (`small`, `medium`, `large-v3-turbo`), optional `language`.
Response: `{"text": "..."}`.

### Embeddings

`POST /v1/embeddings {"model": "e5-small-en-ru", "input": ["passage: ...", "query: ..."]}` -
OpenAI response (`data[].embedding`). The client keeps adding the e5 `passage:`/`query:`
prefixes itself, as soul_memory.py does now.

### Emotions

`POST /sow/emotions {"input": ["text", ...]}` ->
`{"data": [{"label": "joy", "id": 26, "score": 0.81}]}`.

## VRAM budget

The installer fixes a budget per component from the GPU's total VRAM; the speech service
enforces its share at runtime.

```
total VRAM
  - reserve        desktop/compositor on the same GPU: 1 GB if it drives a display, else 0.3 GB
  - speech share   CUDA context + resident STT + the largest enabled TTS (+ RVC if enabled)
  = LLM share      weights + KV cache at the chosen context + compute buffer
```

Measured on an RTX 5060 Ti 16 GB (CUDA 12.8 wheels, 2026-10-25); `/sow/status` reports the
live figures per loaded model:

| Component | VRAM |
|---|---|
| CUDA context of the speech process | ~0.5 GB |
| faster-whisper small (fp16) | 0.6 GB |
| Kokoro | 0.3 GB |
| Qwen3-TTS 0.6B CustomVoice / Base (bf16) | 2.2 / 1.9 GB |
| Qwen3-TTS 1.7B CustomVoice (bf16) | 4.1 GB |
| XTTSv2 | 1.5 GB at load, more while generating |
| RVC (hubert + voice model) | ~1.2 GB (loaded on the first request) |
| Silero TTS, e5-small, go-emotions | CPU, or a few MB |

Speech service policy: STT stays resident; one heavy TTS (XTTS, Qwen3) at a time; least
recently used models are unloaded when a load would exceed the share; a request that
cannot fit even after unloading fails with `out_of_vram` instead of pushing other models
to the CPU silently.

The LLM share is what the installer's model picker uses: it lists only catalog models whose
weights + KV cache at the default context fit into it.

## Client integration points

The client keeps the current class and function names so the rest of the code (and
upstream merges) change as little as possible:

| Current | Becomes |
|---|---|
| `text_to_speech.py` engine classes (`XTTSv2_SOW_System`, `KokoroTTS_SOW_System`, ...) | Same classes and method signatures; they read the character config as now, call `/v1/audio/speech`, write the wav to the same local path and return it. Workers, lip sync and replay are untouched. |
| `speech_to_text.STTWorker` (faster-whisper) | Same QThread; `run()` posts segments to `/v1/audio/transcriptions` |
| `speech_to_text.AudioInputWorker` (Silero via torch.hub) | Silero VAD through `onnxruntime` with the ONNX file already in the repo |
| `embedding_provider.get_embedder()` | Returns a remote embedder whose `.encode(texts, convert_to_numpy=True)` calls `/v1/embeddings`; the existing "unavailable" fallback covers an offline server |
| go-emotions in `interface_signals.detect_emotion`, `sow_system_signals` | `/sow/emotions`; neutral when the server is offline |
| `torch.cuda` checks in main.py, interface_signals.py | `/sow/status` |
| Local LLM (`local_endpoint.py`) | Unchanged external mode, base URL = gateway |
| Models Hub downloads to `assets/local_llm` | `/sow/llm/download` + job progress |

Client settings: `main_settings.server_url`, `main_settings.server_cert_sha256`, token in
`api.json` as `SOW_SERVER_TOKEN` (also used as `LOCAL_LLM_API_TOKEN`).

When the server is unreachable the client still starts: cloud providers keep working, local
features show "server offline" and retry in the background.
